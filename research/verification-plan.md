## 2. V0：可执行评测夹具的结构设计

> 评审要求：把合成文件、标准答案、条款定位、证据关系和预期状态转换做成**能反复运行的测试集**。不是一堆散文件，而是一个目录约定 + 判分器 + 回归比对三件套。

### 2.1 目录约定（fixtures/）

```
fixtures/
├── corpus-A/                      # 主夹具（test-plan §1：25 埋点回归基准；v0.2 已建成）
│   ├── files/                     # 原始文件（A.docx / B1.pdf / B2.pdf / B3.xlsx / C-补遗.docx / 企业资料 13 件）
│   ├── ground-truth/
│   │   ├── requirements.jsonl     # 标准答案：25 埋点每条 {gt_id, clause_no, category, anchors[](可多文件多锚点), params, expected_policy}
│   │   ├── evidence-links.jsonl   # 证据期望关联：{gt_id → ev_file, valid_until, 期望矩阵结论(含过期件/缺失项的 not_eligible)}
│   │   ├── sections.jsonl         # 章节分类法：{id, type, related_gts}（TC-09 影响面断言的引用基准）
│   │   └── conflicts.json         # 预期冲突对（A/C 双版本报价上限）
│   ├── defect-drafts/             # TC-05 缺陷样本（8 类确定性缺陷草稿 + defect-map.json 映射；草稿内无规则标记）
│   ├── expected-transitions/       # 每个 TC 的预期状态转换序列：{tc_id, calls:[工具+参数摘要], assert:[状态机断言]}
│   └── manifest.json              # 全 fixtures 文件 sha256 清单（夹具自身完整性，v0.2 起覆盖 queries/corpus-R）
├── corpus-R/                      # 真实结构分布测试集（v0.1 已建 D1/D2/D5 三层共 5 件——确定性合成，复刻结构特征；D3/D4/D6 待真实样本去标识化）
│   ├── D1-tables/    D1a 合并表头跨页表.docx + D1b 宽表公式.xlsx
│   ├── D2-nonbody/   D2a 非正文条款.docx（页眉页脚条款/文本框/批注/修订）
│   └── D5-scanned/   D5a 全扫描双栏盖章.pdf + D5b 图文混排.pdf
└── queries/
    ├── exact-25.jsonl             # TC-02 精确查询集（含期望命中文本与命中文件）
    └── eval-set.jsonl             # 检索/生成评估集（借 ark evals 结构：valid/invalid-fabrication）
```

**反标记回声纪律（v0.2 审计修正）**：语料正文（A/C/缺陷草稿/证据件）内**禁止出现任何 GT/规则标记**——否则抽取器靠标记回声即可虚高召回。判分器（grade.py）召回判定只认**对齐器**（clause_no / 锚点摘录互含 / 唯一参数值），运行产物自报的 gt_id 无法对齐的记 unverified 不计入召回；"标记回声伪造召回"已入判分器破坏注入自测。


### 2.2 判分器（scripts/grade.py，开发于 M1）

- **输入**：夹具目录 + 一次完整流水线运行的产物库（REQ/EV/CMP/SEC/发现）+ 工具调用轨迹。
- **判分项**：①召回（REQ vs ground-truth，按 gt_id 对齐——允许条款合并但必须包含）；②精确匹配命中；③矩阵 policy 一致性；④引用存在率；⑤状态转换序列比对（expected-transitions 逐条断言）；⑥确定性规则命中（8 类）；⑦幂等重放 totals 不变。
- **输出**：`report.json`（逐项指标 + 失败明细 gt_id 级定位）+ 与上次运行的 diff（回归比对）。
- **纪律**：判分器不调模型、不解析自然语言语义（只做 ID/字段/状态比对）——判分本身必须确定性。

### 2.3 预期状态转换的记录方式

每个 TC 的 expected-transitions 声明：初始状态 → 工具调用序列 → 每步后断言（项目状态/章节状态/DIRTY 集/BLOCKER 计数）。断言失败即状态机回归。TC-06/TC-08 的中断点用标记注入（在第 N 次工具调用后 kill）。

### 2.4 跨文档一致性检查（scripts/xref_check.py）

以 risk-register 追溯矩阵为单一真源，机器检查：①每个 R-* 在 risk-register 表、追溯矩阵两处定义一致；②矩阵引用的 TC-* 在 test-plan 中存在且风险映射列双向对齐（本轮 R-11/R-14/TC-08 三处错误即此类检查的用例）；③AD-* 引用在 architecture-decision 中存在；④MCP 工具名在契约文档中存在。**每次文档变更跑一次**——防"改了测试忘了改风险册"这类漂移。

### 3.2 V2：补遗/答疑/版本影响面计算

**验证内容**：以 TC-09 为骨架扩展为影响面矩阵实测（EXP-2）：

1. **变更类型覆盖**：条款新增 / 修改 / 删除 / 相互矛盾（D3 层真实补遗链）四种变更，各自应触发哪些下游重查——验证 content_version 依赖追踪是否覆盖：证据绑定、矩阵行、章节、评分结论、资格判断五类下游。
2. **级联场景**（评审点名的场景）：补遗修改**开标日期** → 资质有效期断言、投标截止时间、受影响章节、DIRTY 集是否**一起**更新，避免新旧版本混合。断言：全项目有效期重检后，原 EXPIRED 判定若翻转（资质从过期变有效），矩阵与已起草章节必须标 DIRTY。
3. **无关不重跑**：变更影响面外的章节（人工核对清单）不得出现在重跑集——防"全量重跑掩盖影响面错误"。
4. **矛盾终裁**：D3 层"补遗 A1 说 X、答疑 Q2 说非 X"的冲突，验证 conflicts 双向登记 + 人工裁决记录（裁决前相关章节不得 ACCEPTED）。

**通过标准**：影响面断言表（每变更类型 × 每下游类型）全绿；级联场景零新旧混合（证据指纹/版本戳断言）；无关章节零误伤。

|---|---|---|
| 章节多次重写后引用如何保持有效 | 同一章节重写 5 轮，断言：业务侧 content_ref 不变或显式换版；条款/证据引用不悬空 | BlockId 锚点（结构变化后仍可解析）+ expect 乐观并发 + 块删除显式 reject（doc-engine-audit §2.1）；证据 Locator 带登记时刻指纹，"位置在但内容换"二级失效（§2.2） |
| 撤销/恢复/另存/重开后条款—证据—文档关联如何维持 | 引擎侧 undo 到旧版、外部重载 adopt、另存重开，各操作后跑证据链完整性检查 | degrade_linkage **只降不升** + 静默重绑禁令（恢复必须显式重验通道）；RefreshBody/ReverifySource/ReverifyClaim 命令已在（八步闭环） |
| 导出失败或保存中断时，业务状态与文档状态如何一致 | 中断注入：导出中途 kill / sidecar 写盘失败 / 版本冲突并发写 | 业务状态 EXPORTED 必须以产物 sha256 落库为界（两阶段 RENDERED→CONFIRMED）；引擎侧 publish 原子发布（tmp+rename）+ ExpectedVersion::Exactly 乐观并发 + Succeeded/Failed 才入幂等表 |

**通过标准**：三问各有断言脚本入库（并入 expected-transitions），中断注入后零"业务态=EXPORTED 而产物缺失/不匹配"。

**执行结果（SEMUL v1.0，2026-10-24，脚本 scripts/v3_integration.py，证据 artifacts/v3/，回归入口 run_tests T9）**：

| 问 | 结果 | 关键断言（引擎语义复刻：LinkageLedger = evidence.rs 有状态迁移；ExportGate = 原子发布 + sha256 落库为界） |
|---|---|---|
| Q1 多轮重写引用保持 | **全绿** | 5 轮重写循环：每轮恰一链降级（其余 valid——锚不跨链误伤）；全 CIT- 书签零悬空；显式重验通道逐轮恢复全 valid |
| Q2 撤销/恢复/重开维持 | **全绿** | **只降不升**：undo 恢复了内容，Stale 也不自发回升（需显式重验）；外部修改重开检测指纹变化但不静默 adopt（OfferChoice → 业务默认转人工，doc-engine-audit §5.3） |
| Q3 导出中断一致性 | **全绿** | 两阶段确认：渲染后确认前中断 → 业务态停 EXPORTING、零"EXPORTED 而产物缺失"（不变式：EXPORTED ⟺ sha256 落库）；恢复重导幂等（同产物 sha） |

**口径**：三问断言验证的是 doc-engine-audit §5 映射契约的**设计语义**（与 V1-b R2/R3 同源互补——V3 补齐有状态只降不升与两阶段导出面）；引擎本体（Rust）接入后按同一断言脚本升级 ENGINE_RUN。

## 4. EXP-1：最小架构对照实验（Skill+MCP+状态机 vs Dify 工作流）

> 评审指出：AD-01 的论据（DSL 跨版本兼容问题）只能证明**版本迁移存在风险**，不能单独证明 Dify **无法实现**补遗回退或章节重跑。补最小对照实验，不重做调研。结论形态应为"在这个业务场景下，实测维护与恢复成本更低"，而非"某个仓库有缺陷"。

**实验设计**（同一操作者在 2~3 天内可完成的规模）：

| 场景 | Skill+MCP+状态机 | Dify 工作流 | 记录指标 |
|---|---|---|---|
| E1 导入招标文件并抽取条款 | 用 M1 的 import/extract 两工具走通 | Dify DSL 建工作流：文件上传→解析节点→输出条款 JSON | 实现耗时、代码量、失败重试路径 |
| E2 补遗到来后识别受影响章节 | TC-09 影响面逻辑（DIRTY 标记） | DSL 内实现等价逻辑（条件分支/变量传递/子流） | **能否表达**；表达成本；状态在哪 |
| E3 任务中断后恢复 | 状态机断点续跑（TC-06） | kill 后重跑：Dify 会话/会话历史能否续；需哪些人工步骤 | 恢复步骤数、数据损失 |
| E4 修改一个业务规则后的维护成本 | 改一条确定性规则（如有效期基准从开标日改投标截止日）并回归 | 改 DSL 对应节点并处理版本兼容 | 改动量、回归面、是否触碰平台升级 |
| E5 状态/证据/审计日志能否独立迁移 | 导出业务库 JSON → 新环境重放（幂等键验证） | 从 Dify 平台库提取业务状态 → 干净环境重建 | 可提取面、残留面、耗时 |

**判定与记录**：每场景记录"能否实现/成本/恢复性/迁移面"四行事实；不预设胜负。若 Dify 在 E2/E3 也能低成本实现，AD-01/AD-02 的理由区按实测改写（决策仍可维持路径 A——依据换为实测维护成本，而非缺陷指控）。**E5 结果直接回填 R-12 的验证列**。

**范围约束**：只验有争议的编排选型；不重复已有充分依据的决定（KBAdapter 选型 AD-03、图编排否决 AD-04 不重验）。

## 5. 六个分析方向的落地任务索引（评审排序）

### 5.1 文档解析与最终 DOCX 导出的真实能力 → V1（§3.1）+ doc-engine-audit
最高优先级。已展开为 V1-a~d 四段验证；引擎能力与差距（G1 目录域/G2 样式面/G3 元数据清零/G8 渲染复验）见 doc-engine-audit §4——**G1/G2/G3 属引擎侧缺口，需与引擎团队对齐排期**（能力需求清单已同步用户）。

### 5.2 补遗、答疑和文件版本的影响面计算 → V2（§3.2，EXP-2）
现有 DIRTY/content_version 设计继续深化为影响面断言表；重点测开标日期级联与矛盾终裁。

### 5.3 标书业务与文档内核的集成边界 → V3（§3.3）+ doc-engine-audit
不要只研究 MCP 如何调用文档引擎——**研究两个系统如何共同维护版本与证据关系**。审计结论：引擎的证据三态/只降不升/显式重验/原子发布/乐观并发与标书业务设计同构，集成以映射为主（doc-engine-audit §5）；原型三问待断言脚本。

### 5.4 安全威胁模型与人工审批边界 → S1
现有 R-09（出域）/R-13（注入）之外补威胁建模，最小面：
- **文件敌意面**：恶意 Office/PDF（宏/OLE/JS 动作）、压缩包炸弹、解析器崩溃——引擎侧已有容器门/消毒链/限额/沙箱（doc-engine-audit §2.7，可直接继承）；业务侧核对：上传面限类型限大小、失败件隔离已有。
- **越权与外发**：企业资料库按项目隔离的访问范围；工具层无任意路径（对照引擎 PathPolicy 允许列表模式）；外发域名白名单；审批绕过——**最终导出/提交必须人工门禁**（引擎 ReviewPolicy 的 human: 前缀门禁模式直接复用到审批动作，AI 操作者不可改审校态）。
- **提示注入纵深**：文件内容一律数据化（不可信）；工具参数化（Agent 无 shell/无自由 SQL）；已知模式扫描仅作告警不作防线（L3 残余——不可穷举）。
- **日志泄露**：证据摘录/sidecar 属敏感面（引擎侧已是本地纪律）；业务侧日志脱敏清单。
产出：**docs/threat-model.md（v1.0 已交付）**——15 威胁 ×（面/引擎继承/业务补充/测试锚点/状态）+ 信任边界五级 + 人工审批强制点矩阵（5 动作×双层门禁）；建模发现 2 个真实 GAP：T-03（bid-parse 压缩包炸弹限额未挂引擎三门）、T-04（子进程无超时挂死 DoS）——登记为解析器加固待办（真实用户文件接入前完成）。

### 5.5 采购规则与业务边界 → S2（需用户裁决）
合成样本集中于工程服务类政府采购。**待用户输入后钉死 MVP 边界**：政府采购 / 工程招投标 / 企业采购 / 行业技术服务，四选一或分期。裁决后产出：规则来源清单（法规/范本版本+适用地区+更新时间）、人工复核责任矩阵、系统"不确定即停"清单（何时必须升级人工而不是猜）。**不过早建通用规则引擎**——规则集按场景显式版本化（对应 risk-register L2 规则解释风险）。

### 5.6 模型、检索与端到端效果评测 → S3（test-plan §5 已铺开）
指标集：条款召回率、误判率（矩阵 policy 错判）、引用支持率（§5.3 人工协议）、人工返工量（修订任务数×耗时）、执行时间、token 成本、重跑稳定性（§5.4）。比较口径（评审原文）：**同样的文件下，哪个方案更少漏项、更少错误承诺、需要多少人工复核、成本多少**——不做"能否生成"式的演示性评测。

## 6. 验证状态词典（全部文档统一口径）

| 标注 | 含义 | 使用处 |
|---|---|---|
| `VERIFIED_SOURCE` | 结论有开源仓库源码/官方文档一手证据（引用带仓库+commit+文件路径） | workflow-audit、repository-matrix、doc-engine-audit |

| `PARTIAL` | 部分已验（v1.0 新增）：对应链路的一段已自动验证，其余待后续阶段——细节入 risk-register 追溯矩阵注记块，不得整段标 TESTED | 追溯矩阵"测试结果"列（R-01/R-04/R-05/R-11 首批）、各 V* 分段状态 |
| `DESIGN_ASSUMPTION` | 设计推断，未经实现验证——可能被实测推翻 | 各设计文档中待验机制（如影响面规则完备性） |
| `PENDING` | 计划中，未开始 | 本计划全部条目当前态 |
